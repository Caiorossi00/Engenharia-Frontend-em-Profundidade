Em uma aplicação react com redux, especialmente em uma arquitetura enterprise legada, uma mesma funcionalidade pode envolver estado global, regras de negócio, comunicação com APIs e apresentação visual. Se todas essas responsabilidades forem colocadas no mesmo componente, o código rapidamente se torna difícil de compreender e modificar. A separação entre duck, screen e componentes visuais existe justamente para dividir essas resposabilidades e criar limites claros entre cada camada.

O duck representa a camada responsável pelo estado e pelos fluxos do redux. É nele que normalmente ficam os action types, action creators e reducer relacionados àquela funcionalidade. Dependendo da arquitetura adotada pelo projeto, também podem existir dentro dele ou próximos a ele os fluxos assíncronos, como thunks responsáveis por buscar ou enviar dados para uma API. O principal objetivo é que o duck conheça as regras necessárias para transformar actions em mudanças no estado, mas não precise conhecer detalhes e como a interface será apresentada.

A screen funciona como uma camada de orquestração. Ela conecta o estado global à interface e coordena o fluxo da tela. Em aplicações react baseadas em classes, é comum encontrar uma Screen.js conectada ao redux através do connect, recebendo dados e funções por props. Essa camada pode executar ações durante o ciclo de vida, disparar carregamentos iniciais, responder a alterações de estado e preparar os dados necessários para os componentes visuais.

Por exemplo, ao abrir uma tela de edição, a screen pode executar uma ação para buscar determinada entidade. O duck controla o fluxo redux essa operação: dispara a chamada assíncrona, trata os estados de carregamento e sucesso e atualiza a store. Quando o estado muda, a screen recebe os novos dados e os repassa para o componente visual responsável pelo formulário.

O componente visual, por sua vez, deve se preocupar principalmente com a apresenteção e interação da interface. Ele recebe dados através de props e informa eventos ao componente responsável pela orquestração. Um formulário pode receber values, loading, errors, e funções como onSubmit, sem precisar saber de onde esses dados vieram ou como o redux está estruturado.

Dessa forma, podemos enxergar o fluxo como uma divisão de responsabilidades: o duck controla o estado, a screen coordena o comportamento da tela e o componente visual representa a interface. A comunnicação acontece através de propriedades e funções, evitando que o componente visual precise acessar diretamente a store ou conhecer detalhes da API.

Essa separação é especialmente importante em código legado porque evita que a manutenção de uma parte do sistema exija alterações em todas as outras. se a estrutura do redux mudar, o componente visual pode continuar funcionando desde que a screen preserve a interface de props esperada. Da mesma forma, uma alteração visual no formulário não precisa modificar o reducer ou os fluxos assíncronos do Duck.

Isso também facilita a reutilização. Um mesmo componente visual pode ser utilizado por diferentes screens, desde que receba as propriedades esperadas. A screen pode preparar os dados de maneiras diferentes sem obrigar o componente visual a reconhecer essas diferenças.

O objetivo dessa arquitetura, portanto, não é criar camadas apenas por formalidade. A separação existe para estabelecer fronteiras de responsabilidade. O duck trabalha com estado e transições, a screen trabalha com orquestração e integração, e os componentes visuais trabalham com apresentação e interação. Quando essas fronteiras são respeitadas, mesmo uma aplicação react legada consegue manter um fluxo mais previsível, permitindo que cada parte seja compreendida e modificada sem carregar desnecessariamente as responsabilidades das outras.
